# The Linux image serving the Zebratlas release under a 4 GB cap (4 October 2026)

Will zebratlas.org/sparql (a container capped at 4 GB) load and serve the release with
this image? Yes, with the margin below.

- Image: `nrese-cert:5c54759`, built from the root Dockerfile with
  `NRESE_TARGET_CPU=portable` (ID `sha256:88ed4b2357c8…`).
- Data: `zebratlas-kg-v0.1/graph.ttl` (2.17 GB of Turtle, sha256 `990e5b02…`).
- Machine: the main PC, Docker Desktop (WSL2).
- Check: [`image-cap-check.sh`](../../probes/image-cap-check.sh) with `--memory 4g --memory-swap 4g`.
- Defaults: reasoning off, the default budgets (process memory 75 % of the cap, bulk load 25 %).

| Step | Result | Of the 4 GB cap |
|---|---|---|
| Bulk load (parallel loader) | 22.7 M statements in 20–28 s | peak 1.78–1.87 GB |
| Store on disk | 652 MB | – |
| Start to ready | 0.6–0.9 s; 1.9 s after a restart | 17 MB after start |
| 12 queries, result cache off | first run ≤ 0.13 s each; repeats ≤ 0.07 s (Q09, the heaviest), the rest ≤ 0.01 s | – |
| 8 concurrent streams × 3 rounds, cache off | all answered, no OOM kill | peak 1.19 GB |
| The same, cache on | all answered | peak 0.43 GB |

- **Answers:** byte-identical with the cache on and off.
- **Oxigraph:** on candidate.7, Oxigraph 0.5.11 gives the same answers to all ten questions.
  - Q02 and Q05 needed equivalent rewrites.
  - Q09 needed its parts: the edge records, and the records with each of the five fields. All six sets are identical, and no edge record lacks a field.
  - Oxigraph takes more than 600 s on Q09 itself.
- **Six of the twelve queries return no rows** (01, 02, 04, 05, 08 reconstructed provenance, 09 rejected identities), as on candidate.7 and in Oxigraph: the data has no matches (the deployment's task list
  has exporting the relationship types the queries need as its first step).

What this does not cover: the production host's own memory (API and web beside the store),
its network limits, and datasets larger than this release.
